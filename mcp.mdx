BreachLens has two relationships with the Model Context Protocol (MCP). **Today** it *scans* MCP servers as a first-class target — that's [MCP server scanning](/ai-identity/mcp-servers), and it's shipped. **On the roadmap**, BreachLens itself will *expose* its findings and scan operations as an MCP server, so agents like Claude, Cursor, and Windsurf can query and act on your security state natively — without a custom API integration.

<Note>
  **Coming in a future release.** The tools below are planned, not yet available. Today, drive BreachLens from the [REST API](/api) or the [CLI](/cli).
</Note>

## Planned agent-facing tools

Subject to change:

- `list_findings` — query findings by severity, scan type, target, or attack-path membership.
- `simulate_fix` — dry-run a proposed patch and see which downstream correlation links it would break before opening a PR.
- `trigger_scan` — kick off a scan against a target the agent has been granted access to.
- `get_attack_path` — fetch a chain by id, with the same evidence the UI renders.

When this ships, the same probes BreachLens runs against third-party MCP servers will run against its own MCP surface as part of every release.

## Why this matters

MCP is the connector layer for the next generation of AI workflows, and most operators are wiring agents into production tools with little visibility into prompt-injection, tool-poisoning, or token-theft risk. BreachLens already treats every MCP server you register as the same kind of asset as a repository or a domain — inventoried, scanned, correlated, and reported. Exposing BreachLens *as* an MCP server closes the loop: the agents writing your code can query the security state of what they build.
